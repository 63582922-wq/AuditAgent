# 资料视觉识别准确率优化计划

日期：2026-06-28

## 结论

上传资料需要专门的资料视觉准确性 Skill。通用 OCR 只能证明“模型看过图片”，不能证明“审核所需字段被准确识别”。尤其是到场确认单、现场确认单、签到/签名单等手写资料，如果识别不准，应进入补充资料或人工复核，而不是继续自动判定通过。

## 当前链路判断

现有项目已经具备视觉 Agent、GLM-OCR 入口、图片/PDF 扫描页分流和合规字段抽取，但之前缺少四个产品级能力：

- 图片质量门控：低清、低对比、低细节图片没有结构化质量评分。
- 字段级置信度：不能只用整页 confidence 代表会议编码、到场确认、讲者服务时长、签到人数等关键字段。
- 手写件策略：手写签名、手写确认、到场确认单没有独立高风险路径。
- 评测闭环：缺少基于真实样本的字段级准确率评测。

## 已落地的第一层能力

新增 `material_vision_accuracy` Skill，接入合规视觉解析统一出口：

- `vision_quality`：记录尺寸、质量分、低清/低对比/低细节 flags。
- `recognition_plan`：标准 OCR 或多轮字段级 OCR 的执行计划。
- `field_confidence`：按关键字段输出置信度。
- `manual_review_required`：手写风险、低质量图、关键字段缺失或低模型置信度时触发复核。
- `review_reasons`：解释为什么不能自动通过。

## 产品级目标链路

1. 上传案件资料文件夹。
2. 主 Agent 预览资料结构并分派文本/视觉资料。
3. 视觉 Agent 执行 OCR 和字段抽取。
4. 资料视觉准确性 Skill 判断图片质量、字段置信度和手写风险。
5. 低置信资料进入补充资料/人工复核入口。
6. 规则引擎只消费“字段值 + 证据来源 + 字段置信度 + 复核状态”。
7. 输出 Excel/PDF 交付物时保留关键证据和需复核原因。

## 下一阶段必须补齐

- 字段裁剪识别：对确认单的会议编码、服务时长、观察结论、签名区域分别裁剪后重跑 OCR。
- 多模型交叉：对手写和低清资料支持第二视觉模型或专门手写 OCR 引擎。
- 真实样本评测集：从 FX 样本中建立 golden labels，按字段计算 exact match、F1、漏识别率和误识别率。
- UI 闭环：资料池中展示低质量/手写风险标签，主 Agent 对话中直接发起“请补充清晰图片/请人工确认字段”。
- 输出审计轨迹：交付物中标注哪些 Finding 依赖低置信视觉字段。

## 并发与多模型策略

结论：图片识别应该作为异步 job 执行，但 job 内部可以有限并发，例如 3-5 个图片任务同时跑。用户界面不应该同步阻塞等待所有图片 OCR 完成。

原因：

- 项目当前使用的 GLM-OCR `layout_parsing` 是单文件请求形态，参数是一个 `file`，文件可以是图片或 PDF；它不是一个“多张独立图片数组”的批量接口。
- GLM 文档建议多页 PDF 可拆分后并发调用以提升速度，这与“每张图一个 OCR 子任务 + 并发池”一致。
- OpenAI 视觉接口可以在一个请求中放入多个 image input，但这更适合跨图问答或比较，不等于最适合审计级 OCR。审计场景更需要每页/每字段的证据坐标、置信度和可重跑性。

推荐策略：

1. 每个文件先做轻量预检：尺寸、清晰度、对比度、是否疑似手写、是否长图/多页。
2. 普通图片：单模型 OCR + 字段 schema 抽取。
3. 高风险图片：主 OCR + 独立 verifier。verifier 不重复同一提示词，而是按字段核对“证据是否支持该字段值”。
4. 手写确认单/签到类：字段级裁剪重识别，必要时引入第二视觉模型或手写 OCR 引擎。
5. 不一致时：由 adjudicator 只裁决差异字段；仍低置信则进入人工复核/补充资料，而不是继续自动通过。
6. 并发控制：每个案件默认 3-5 个视觉任务并发，按供应商限流、失败率和队列长度动态降级。
